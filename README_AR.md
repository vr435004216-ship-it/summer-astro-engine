# Summer Astro Engine 2.0.0

نسخة مستقلة قابلة للتشغيل عبر API وواجهة متصفح وCLI. أعيد بناء التفسير فوق Swiss Ephemeris، مع الحفاظ على حساب Whole Sign وLahiri وVarga وVimshottari وتصحيح UTC ومعالجة Solar Return لأي شهر ميلاد. ليست مجرد مواصفة.

## تشغيل سريع

Python 3.12 ومترجم C/C++ لبناء pyswisseph عند عدم توفر wheel:

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest -q
export SUMMER_API_TOKEN="your-private-service-key"
python -m uvicorn summer_astro.api:app --host 127.0.0.1 --port 8000 --workers 1
```

افتح http://127.0.0.1:8000 ثم أدخل المفتاح. اترك هامش وقت الميلاد فارغًا إن لم تعرفه؛ ستظهر النتائج غير المؤهلة بسبب نقص معلومات الحساسية. لا تضع هامشًا صفريًا لتحسين النتيجة دون أساس.

تشغيل Docker:

```bash
export SUMMER_API_TOKEN="your-private-service-key"
docker compose up --build -d
```

Compose يربط المنفذ محليًا ويستخدم volume دائمًا للسجل. للنشر على استضافة: شغّل نفس الحاوية خلف HTTPS مع المفتاح ومتغير SUMMER_DB على قرص دائم. عامل واحد مقصود لعزل حالة Swiss Ephemeris؛ الطلبات المتزامنة الزائدة تحصل على 429 وتعيد المحاولة بنفس المدخل. لا مفتاح افتراضي. /forecast و/runs و/outcomes و/metrics و/policy و/schema محمية، /health والواجهة دون بيانات نتائج متاحة دون مصادقة.

لا تعرّض SQLite أو ملفات البيانات للويب. لخفض البيانات المعروضة يمكنك تقييد الوصول إلى الخدمة بمستخدمها الوحيد. لا تخزّن مفتاح الخدمة في مستودع أو في المتصفح.

## CLI

```bash
python -m summer_astro.cli forecast request.json --output reports/forecast.json
python -m summer_astro.cli ablation request.json --output reports/ablation.json
python -m summer_astro.cli evaluate evaluation.json --output reports/evaluation.json
```

## ما تم تنفيذه

- مسار tropical للتوقيت الغربي ومسار Lahiri لـVimshottari والفارغا؛ بياناتهما منفصلة.
- lineage وdependency groups وقواعد مسجلة؛ caps داخل العائلات، وإزالة التكرار قبل الجمع.
- ontology تفصل السفر والتعليم والمجالات المهنية والمالية؛ درجات دعم متعددة وليست احتمالات.
- Natal/Varga خصائص ثابتة في birth_calculations؛ ليست مولدات أحداث ولا تضيف وزنًا زمنيًا مستقلًا.
- خلفية سنوية/داشا منفصلة عن triggers؛ عتبة دخول وخروج وذروة يومية. حدود الداشا وحدها لا تُصنع منها أحداث.
- مقارنة فرضيات merge/separate، ومنع الدمج لمجرد الوقت أو عبر سلسلة تجاور غير محدودة.
- axes مستقلة، وأفعال حرفية فقط إذا دعمتها حالات مرتبة لنفس الموضوع. التفسير الفلكي العام لا يختلق ترقية أو زواجًا.
- ambiguous/mixed/insufficient-data/no-qualified-forecast، مع counterevidence وبدائل.
- جميع الإشارات والنوافذ والمرشحين محفوظة؛ max_display لا يغير سجل الحساب.
- سجل SQLite append-only وidempotent، مع recorded_at الفعلي وas_of وhash وإصدارات الحساب والسياسة والمنطقة الزمنية.
- فصل astrology_only عن context_assisted؛ معلومات السياق تحمل known_at وتُرفض عند تسربها بعد as_of، وتُوسم provided_not_predicted.
- فصل occurrence عن classification وعن personal_relevance؛ occurrence_probability=null ولا نموذج شخصي متعلم في هذا الإصدار.
- تقييم one-to-one، فترات رصد لازمة، pending عند عدم نضج النافذة، split زمني مع purge حسب هوية الحدث، random baseline يحفظ المدة والموسمية، وablation لكل عائلة.
- JSON صارم ونص حتمي من نفس الحقول؛ لا LLM في مسار القرار.

## حدود النسخة

هذه نسخة تشغيل تجريبية كاملة لمسار القواعد، وليس إثباتًا أن الفلك يتنبأ بالأحداث. الأوزان والعتبات الافتراضية اختيارات هندسية معلنة في policy.json لم تُدرّب ولم تُعاير. لا تعطِ score معنى احتمال. اختبارات البرنامج تثبت السلوك البرمجي فقط؛ prospective validation يبدأ من سجلات جديدة منشورة قبل الأحداث، وليس من تعديل تاريخ معروف.

دلالات البيوت وقواعد الاتجاه مسجلة باعتبارها فرضيات تفسير. قواعد D4/D9/D10/D16 محفوظة كحسابات سياق؛ لا إضافات «تأكيد» مستقلة منها. Occurrence لا يمكن إعطاؤه احتمالًا متعلمًا دون سجل أحداث وفترات هادئة موثقين؛ النظام يفحص qualification ثم يمتنع أو يعرض تنشيط مجال مع بدائل. أي نموذج احتمالي أو شخصي جديد يحتاج إصدارًا واختبارًا منفصلًا؛ تشغيله من policy وحدها مرفوض.

الدقة الافتراضية يومية؛ الجذور الدقيقة للعبور تظهر في raw_signals إن أمكن حصرها حسابيًا، لكنها لا تعني دقة دقيقة لوقوع الحدث. uncertainty sensitivity شبكة حتمية وليست توزيعًا احتماليًا. الفارغا تتأثر بوقت الميلاد؛ الاستقرار العام محافظ وقد يمنع عرض مرشحين في مجالات أخرى أيضًا. solar_return_location= birth_location افتراض معلن؛ لا تخمين لموقع المستخدم يوم العودة.

حدود البيانات المرفقة: الميلاد من 1801 حتى 2098، 1095 يومًا كحد أقصى للطلب. لا تشخيص طبي ولا نصيحة مالية/قانونية من إشارات المجالات.

بعض مسارات التحقق تستبعد الحالات غير المرصودة والتوقعات المتأخرة. التطابق الحالي exact-domain/class + interval-overlap؛ عرض النوافذ والتغطية يقاسان معه حتى لا يختبئ أثر النوافذ العريضة. عند غياب عينات قابلة للتقييم precision/recall=null. تشغيل ablation ينتج نتائج المقارنة، لكنه لا يقرر قيمة الطبقة دون الحقيقة المرجعية.

## الإصدار والسجل

أي تعديل policy يغيّر policy_hash وrun_id. السجل يمنع UPDATE وDELETE ولا يسمح بإعادة استخدام ID لمحتوى مختلف. as_of يمثل cutoff معلنًا؛ recorded_at وقت الحفظ الحقيقي هو المرجع للحكم على كون التوقع مستقبليًا. تعديل الأهمية الشخصية أو عدد العرض لا يغير سجل الحساب. نتائج افتراضات المدرسة لا تُعد أدلة مستقلة لمجرد اختلاف أسماء الطبقات.

مرجع الحسابات السابقة: astro_math_core_v1_3.py وSummer_AstroMath_FINAL.zip، مع hashes محفوظة في reports/source_audit.json. النموذج الشخصي السابق ومعاملاته ونسبه التاريخية ليست جزءًا من runtime الجديد.

## الترخيص

الكود الجديد AGPL-3.0-or-later؛ ملفات ومكتبة Swiss Ephemeris وفق إشعاراتها المرفقة. لا تُنشر الحزمة كخدمة مغلقة المصدر تحت المسار المجاني دون مراعاة الترخيص. مصدر الخدمة متاح في الحزمة؛ الترخيص المهني مسار بديل إذا اختير لاحقًا.

الحزمة جاهزة للتشغيل محليًا ولتركيبها في استضافة حاويات. لم تُنشر على عنوان عام؛ لم يُحدد مشروع استضافة أو نطاق لهذه الخدمة. تقارير الاختبارات والتشغيل الفعلي في reports. Dockerfile مرفق؛ لا يُدّعى اختبار build Docker إذا لم تتوفر Docker في بيئة التنفيذ.
